# Changelog

Versions follow the plugin version in `.claude-plugin/plugin.json`. Design notes behind each change are in [DESIGN.md](DESIGN.md).

## 0.7.2
- **Backlog files are written as UTF-8 and checked:** `features-archive`, `bugs-archive`, `feature-plan` and `bug-report` now say to write the backlog files as UTF-8 explicitly and to read them back as UTF-8 afterwards. An ad-hoc script that opened a file with the system's default text encoding saved the `·` of a new row as one invalid byte, and every script that reads the backlog then stopped with a decoding error.
- **A badly encoded line no longer stops the scripts:** `read_lines` reads an invalid byte as a replacement character instead of raising, and `features-status` and `bugs-status` list the file and line numbers under **Data integrity** so the line can be re-saved.

## 0.7.1
- **A just-planned feature or bug can be developed right away:** `feature-development` (Phase 1, B2), `bug-fix` (B2) and `gitflow` (`start <topic>`) no longer stop on uncommitted changes confined to `<backlog>/` — the row and brief that `feature-plan` or `bug-report` just wrote. The new branch carries them along. Any other uncommitted change still stops the action.
- **Phase 2 no longer runs the whole test suite:** the implementation subagent runs only the tests of the files it touched and never ends its response with a command still running in the background. A full suite can outlast the Bash tool's cap, and a leftover background job made the subagent re-send its hand-back long after Phase 3 had taken over.
- **Review gate G3 is explicit about migrations:** a migration counts as security-sensitive when it adds or changes a policy, grant, role or privileged function, or backfills or rewrites user-owned rows; a purely additive column or index does not count on its own.

## 0.7.0
- **Estimation rubric in `feature-plan`:** the story-point suggestion now follows a fixed rubric instead of a loose list of factors. Reach (one layer starts at `1`, two or more at `3`), then one step up for breadth (eight or more acceptance criteria, or three or more independent flows), for a schema change on a single-layer story, and for real novelty; one step down for a near copy of an existing feature; a result above `8` is a split candidate. The rubric was calibrated on the finished backlogs of two projects: layers, schema change and the breadth of the acceptance criteria tracked the real size of features, while "a new dependency" and the length of the notes did not, so they no longer count. The scale is documented as ordinal, not proportional.
- **`<backlog>/estimation-anchors.md` (optional):** a project can list finished features as reference examples of each value; `feature-plan` reads the file when it exists and names the closest example as the reason. The kit never creates or requires it.

## 0.6.0
- **`feature-plan` asks for the story points:** after drafting the brief it calculates a suggestion (from the number of acceptance criteria, the layers the technical notes touch, schema changes and what is new to the project), asks the user for the number with the suggestion first and marked "(Recommended)" plus its neighbours on the scale, and takes whatever the user answers; a value off the scale is asked again, never rounded. A value the user gave in the request is the suggestion. Effort is no longer drafted silently with the other attribute columns. If the question cannot be asked, the draft marks the number "(suggested, not confirmed)". An `8` or `13` still offers the split.

## 0.5.0
- **Effort is measured in story points:** the Fibonacci scale `1`/`2`/`3`/`5`/`8`/`13` replaces S/M/L/XL. The column keeps its header, `Effort`, so the skills and scripts that read it by name are unchanged. `8` or more is too large for one story and is offered for splitting (what `XL` was). `feature-plan` drafts points; `features-status` breaks pending features down by points and prints the pending total, and still counts the old sizes (S=1, M=3, L=5, XL=8) in a backlog that has not been converted.
- **`tools/effort_to_points.py`:** converts the Effort column of both feature tables and the legend line in one pass (`--dry-run` to preview, idempotent). `MIGRATING.md` describes it.

## 0.4.0
- **Briefs are user stories:** `feature-plan` writes each new brief as `**As a** <role>, **I want** <goal>, **so that** <benefit>.`, followed by `## Acceptance Criteria` (numbered `AC1`…`ACn`, Given/When/Then, each binary and testable), `## Technical notes` (the concrete mechanism the old single paragraph carried), an optional `## Out of scope` and a `## Definition of Done` section that lists only what is extra for the feature. One story per brief. Existing one-paragraph briefs stay valid and are not rewritten by the skills; `MIGRATING.md` describes how to convert them, together with the Summary of planned rows.
- **Definition of Done file:** `<backlog>/definition-of-done.md` is a project-wide markdown checklist. While it is missing, `feature-plan` asks every run whether to write it (now, or a starter drawn from the project's docs and workflow, or not now); it never blocks planning. `feature-development` lists each item in its Final Summary and `spec-compliance-check` reports the items it can evidence (advisory, outside the proof totals).
- **`XL` effort:** the scale is `S/M/L/XL`; an `XL` (or a description holding several stories) is a candidate for splitting, and `feature-plan` offers "Split into several features" in its confirmation. `features-status` counts `XL`.
- **Acceptance criteria flow through the pipeline:** `feature-development` tells `openspec-propose` to turn every AC into at least one scenario and asks the implementation subagent for one `ACCEPTANCE:` line per AC; `spec-compliance-check` lists an AC without a scenario or evidence as Unverified.
- **`features-status`:** advisory warnings for a story-shaped brief with no acceptance criteria and, as a note, for a missing `definition-of-done.md`.

## 0.3.1
- **Verifiable skill use:** `code-reviewer`, `database-reviewer`, `security-reviewer` and `spec-compliance-check` stamp the first line of their report with `<!-- backlog-kit: <skill> -->`. The review gate (G6) and the Phase 6S check read the stamp: a report without it, in a project where the skill is installed, is a hand-written report and a failed run (re-spawned once). `SKILL_USED:` alone is no longer enough. `spec-compliance-check` also ends its report with a `Verified N · Failing N · Unverified N` line for the orchestrator to read.
- **`feature-development` reads natural language:** the flags are shorthand for orchestrators, never something a user must type; a plain request ("develop X", "stay on this branch", "commit as you go") is complete, the skill states how it understood it, and all phases run by default.
- **`feature-development`:** a run started on a topic branch the user wants to stay on is handled as `--skip-branch-setup`; a request to commit as the work goes means one `gitflow` commit after each phase that changed files (Phase 7 commits what is left); a phase ledger (one task per phase and gate) is created after Phase 0 and the Final Summary waits for it; archiving always comes after the review gate, tests and spec proof, and always through `openspec-sync-specs` and `openspec-archive-change`; a phase that names a skill invokes that skill.
- **Review scope (gate G0):** not committing, `CHANGED_FILES` is the uncommitted files (untracked included); committing, it is the files differing from `develop` (`develop...HEAD`) plus the uncommitted ones. A clean tree after a commit no longer yields an empty scope. The mode is passed into every review prompt.
- **Consistency fixes:** a build fix to production source (Phase 5) is reported as `PROD_CODE_FIXED` and handled like Phase 3's; `IMPLEMENT: DONE` can follow `ACCEPTANCE:` lines; stale "Phase 2's review" and "Phase 6 cannot start" references now name the Phase 2R gate and Phase 6S; the Phase 6S index row names its file; the foreground guardrail counts seven subagents; the `ARCHIVE_BLOCKED` sentence sits under the Final Summary bullet again; the branch-setup steps are labelled B0 to B4 and the batch-mode branch no longer points at two different steps; `bug-fix` gets the same plain-language, existing-branch, commit-as-you-go, ledger and skills-as-written paragraphs; `README` and `gitflow` describe the review gate, the spec proof and the commit options.

## 0.3.0
- **Review gate (`feature-development`, `bug-fix`):** the code, database and security reviews and the viewport check no longer run at the tail of the implementation subagent. A new Phase 2R, run by the orchestrator (`reference/review-gate.md`, vendored from `shared/review-gate.md`), spawns one clean-context subagent per review. The orchestrator computes `CHANGED_FILES` itself and decides which conditional reviews apply, so a wrong "not applicable" from the implementer can no longer skip one.
- **Verified, not trusted:** before accepting a review signal the orchestrator checks that the dated report exists, that no 🔴/🟡 finding is left unchecked, and that the reviewer skill was actually used (`SKILL_USED:`); a fallback self-review while the skill is installed is re-run, and one without the skill is flagged in the Final Summary. Each gate's outcome is a ledger line (`CODE_REVIEW:`, `DATABASE_REVIEW:`, `SECURITY_REVIEW:`, `VIEWPORTS:`) with a report path or a skip reason.
- **Spec proof in its own subagent (`feature-development` Phase 6S):** `spec-compliance-check` no longer shares a context with docs sync and archiving. The orchestrator opens the report and requires `Failing` and `Unverified` to be 0 before the archive subagent starts; a manual proof while the skill is installed is re-run.
- The implementation subagents now return only `IMPLEMENT: DONE` / `FIX_IMPLEMENTED: DONE`; the next phase waits for `REVIEW_GATE: DONE`.

## 0.2.1
- **`feature-development` Phase 6:** the delta specs of an OpenSpec change now reach the main specs through `openspec-sync-specs`, run before `openspec-archive-change`; a hand-written merge of `openspec/specs/**` is no longer accepted, and the hand-back reports `SPECS SYNCED`.
- **`feature-development` Phase 4:** starts a stopped container runtime (Docker) itself instead of reporting it as a blocker, and applies the change's own pending migrations after a dry run shows nothing else pending (otherwise `E2E_BLOCKED — unexpected pending migrations`). The "never writes to a shared database" guardrail is narrowed to match.

## 0.2.0
- **`gitflow` commit action:** one local commit on a topic branch, on request only, with the file list and message confirmed first. It never pushes, amends or skips hooks. The kit's promise stands: nothing is committed unless you ask.
- **`bug-fix --commit`** (and the same flag on `bugs-batch-fix`): a new Phase 7 asks `gitflow` for one commit per closed bug, holding the fix, its regression test and the backlog move.
- **`bug-fix` phase discipline:** every phase runs or is skipped under its stated condition with a recorded reason; Phase 1 must quote the failing output of the regression test (`RED:` line) or the run is treated as blocked; the Final Summary carries a status table for every phase.
- **`feature-development --commit`** (and the same flag on `features-batch-development`): Phase 7 asks `gitflow` for one commit per completed feature. The same phase discipline applies: every phase runs or is skipped with a recorded reason, the Final Summary carries a status table, and the batch skill must run `feature-development` for every feature and write its report even when working inline.
- **`bugs-batch-fix`:** must run `bug-fix` for every bug, with all its phases, and must write its report even when the work is done inline; a conflict with the user's wishes is settled with `--commit` or a question, never by dropping the skill.

## 0.1.1
- A project that lives in a subfolder of its repository (the backlog at `app/docs/backlog`) keeps its reference docs, `CLAUDE.md` and `README.md` next to that `docs` folder: the reviewers, `spec-compliance-check`, `dependency-upgrade`, `docs-sync` and the conventions say so, instead of assuming the repository root. The architecture reviewer no longer mentions a `reports_dir` setting that did not exist.

## 0.1.0
First public release.

- **Core skills (12):** the planning family (`feature-plan`, `features-next`, `features-status`, `features-archive`, `bug-report`, `bugs-next`, `bugs-status`, `bugs-archive`), `decision-record`, the work pipelines `feature-development` and `bug-fix`, and `gitflow`. The backlog is markdown under `docs/backlog/`; nothing is committed without you.
- **Extras (10, optional):** `code-reviewer`, `security-reviewer`, `database-reviewer`, `architecture-reviewer`, `product-scope-roaster`, `docs-sync`, `spec-compliance-check`, `dependency-upgrade`, `features-batch-development`, `bugs-batch-fix`. Each reads its project-specific checks from a named section of the project's own docs.
- **Conventions:** a fixed set of document locations and a `## Kit conventions` table in the project's `CLAUDE.md`; only `CLAUDE.md` is mandatory ([docs/conventions.md](docs/conventions.md)).
- **Configuration:** `.backlog-kit.toml` with `[paths] backlog_dir` and `[viewports]`, both optional.
- **Tools:** `tools/install.py` (copy install), `tools/vendor.py` (shared files into skills), `tools/migrate_check.py` (read-only check before replacing a project's own skills, see [MIGRATING.md](MIGRATING.md)).
